# 프롬프트 캐시 실측과 설계

> **이 문서의 수치는 시뮬레이션이 아닌 실측입니다. 측정일 2026-11-11(E1~E6)과 2026-11-12(E7), OpenRouter 경유 `google/gemini-3.8-flash`.**
> 측정은 사용자가 `npm run cache:probe -- --real`로 직접 실행했고, 이 문서는 그 결과를 정리한 것입니다.
> 아래에서 **"(원문 필요)"** 로 표시한 칸은 아직 원문 표(`docs/cache-probe-raw-2026-11-11.md`)가 이 저장소에 없어 비워 둔 곳입니다. 추정해서 채우지 않았습니다. 채워진 숫자는 사용자가 원문에서 옮겨 전달한 값입니다.

### 비용 검산

단가(2026-11-11 OpenRouter 확인, USD/1M): 입력 0.75, 출력 3.75, 캐시 읽기 0.075, 캐시 쓰기 0.041667.

```
비캐시 토큰 × 0.75 + 캐시 토큰 × (0.075 + 0.041667)   (÷ 1,000,000)
  = upstream_inference_prompt_cost   ← 사용자 검산: 정확히 일치
```

- 즉 `cached`와 `cache_write`는 **같은 토큰**이고, 그 토큰에 **읽기 단가와 쓰기 단가가 둘 다** 청구된다.
- 캐시 토큰 단가는 입력 단가의 약 15.6%다(0.116667 / 0.75). 할인은 있지만 "읽기만 청구"일 때(10%)보다 5.6%p 덜 싸다.
- 앞 절 초안의 우려("같은 토큰이 두 번 세어져 식이 왜곡될 수 있다")는 이 검산으로 정리됐다: 식이 맞으려면 두 단가를 모두 곱해야 한다.

## 2. 판정

- **확인된 것**
  - 이 모델·경로에서 암시적(자동) 캐시는 11.5K에서도 0이다.
  - 명시적 `cache_control`은 3,555토큰 이하(1,754 / 3,555)에서 실패, 4,159토큰 이상(4,159 / 5,799)에서 동작했다. 문턱은 3,555~4,159 사이다.
  - **E6 판정 = "매 요청 할인" 방식.** 앞부분이 서로 다른 요청 두 개가 각각 처음 보내는데도 첫 요청부터 `cached = cacheWr`(6297, 6520)였다. 같은 접두사를 다시 보낼 때만 읽히는 "재사용"이 아니라, `cache_control`을 붙인 요청은 매번 그 앞부분 전체가 캐시 토큰으로 계산되어 읽기+쓰기 단가로 청구된다.
- **의미**
  - `UsageLog.cachedInputTokens` / `/admin`의 "캐시 적중률"은 이 방식에서 **재사용 비율이 아니다**("cache_control을 붙인 앞부분의 비중"에 가깝다). 그래서 적중률 숫자만으로 캐시가 효과를 냈다고 해석하면 안 된다.
  - 효과는 **비용**(`actualCost`)과 **지연**(ttft)으로 판단한다: 캐시 토큰 단가 15.6% 대 일반 입력 100%. 실제 지연 차이는 아직 측정 전이다 → 4절의 `cache:latency`.
  - 반대로 접두사가 매 턴 달라지는 경우에도(로어북이 바뀌는 등) 할인은 같은 방식으로 붙으므로, 이 방식에서는 로어북 위치가 **할인 유무**를 가르지 않을 가능성이 높다(지연에는 영향이 남을 수 있음 — 미측정).

## 3. 적용한 설정 (2026-11-11 E6 판정 후, 최소 길이는 2026-11-12 E7 뒤 조정)

| 옵션 | 환경변수 | 기본값 | 내용 |
| --- | --- | --- | --- |
| 명시적 캐시 breakpoint | `CACHE_BREAKPOINT` | **1(켬)** (이전 0) | 조립기가 **현재 사용자 입력 직전의 마지막 안정 메시지**에 표시(`cacheBreakpoint`)를 붙이고, `OpenAiCompatAdapter`가 그 메시지를 `[{type:"text", text, cache_control:{type:"ephemeral"}}]`로 바꿔 보낸다. Gemini는 마지막 breakpoint만 쓰므로 한 곳에만 붙인다. |
| 로어북 위치 | `LOREBOOK_POSITION` | `afterFixed`(유지) | 고정 블록·요약 바로 뒤. `beforeInput`(최근 대화 뒤·입력 바로 앞)은 선택지로 남겨 두었다. 로어북이 `beforeInput`이면 breakpoint는 로어북이 아니라 그 앞의 안정 메시지에 붙는다. |
| 최소 길이 | `CACHE_MIN_TOKENS` | **3500** (이전 4096) | breakpoint 앞부분의 (환산) 토큰이 이 값 미만이면 붙이지 않는다. 실측 문턱 구간(3,555~4,159, E7)보다 아래로 잡았다. 문턱 미달 요청에 표시가 붙어도 일반 요금이라 손해가 없다(E7). 환산 계수 0.55는 그대로다. |

- **전송 안전**: 어댑터는 주소가 `openrouter.ai`일 때만 `cache_control`을 보낸다(`supportsExplicitCache`). 다른 OpenAI 호환 서버에서는 표시를 떼고 일반 문자열 content로 보낸다. 내부 표시 필드는 어느 경우에도 제공사로 새지 않는다. 끄려면 `CACHE_BREAKPOINT=0`.
- **추정 비용(`estCost`)**: 위 과금 방식에 맞췄다. `(입력 − max(캐시읽기, 캐시쓰기))×입력 + 캐시읽기×읽기 + 캐시쓰기×쓰기 + 출력×출력`, `cacheWritePer1M`이 없으면 쓰기 항목은 0. 캐시 쓰기 토큰이 읽기 토큰과 **겹친다는 가정**이며 이 모델·경로에서만 검산했다. `pricing.json`에 모델 항목을 넣을 때 읽기(0.075)와 쓰기(0.041667)를 모두 입력해야 위 검산식과 같아진다. 실제 청구액(`actualCost`)이 있으면 `/admin`은 그것을 쓰고 `estCost`는 비교용이다.
- **한계**: 세션 요약이 바뀌는 시점(`SUMMARY_EVERY`마다)에는 접두사가 달라진다. TTL은 5분 고정이고 갱신되지 않는다(문서). `session_id`는 아직 요청에 넣지 않는다. 표시가 동작하면 그 앞부분 전체가 읽기+쓰기 단가(입력의 약 15.6%)로 청구되고, 문턱에 못 미치면 표시가 붙어도 일반 단가(100%)다(E7).

## 4. 도구

| 목적 | 명령 | 호출 |
| --- | --- | --- |
| 토큰 추정 보정 확인 | `npm run tokens:calib [-- --days 30 --model <모델> --min-est 500]` | 없음(개발 DB 읽기 전용) |
| 지연·비용 비교 | `npm run cache:latency -- --real [--rounds 2 --turns 10 --min-tokens 0]` | `--real`일 때만 |
| 캐시 실험 E1~E7 | `npm run cache:probe -- --real [--only E6]` | `--real`일 때만 |
| 캐시 문턱 찾기 (E7) | `npm run cache:probe -- --real --only E7 [--e7-targets 2500,3200,3600,4200]` | `--real`일 때만, 4회 |

- **E7(문턱)**: `cache_control`을 붙인 요청을 약 2.5K, 3.2K, 3.6K, 4.2K토큰으로 1회씩 보낸다. 크기는 영문 더미 텍스트의 글자 수로 맞춘 근사치라서(더미 약 3.16글자/토큰, 2026-11-11 E4·E5 실측에서 역산) 표의 `prompt` 열(제공사가 센 값)을 기준으로 읽는다. 요청마다 맨 앞에 실행별 표식을 넣어 이전 요청의 캐시와 겹치지 않는다. "매 요청 할인" 방식이므로 **처음 cached>0이 되는 크기가 문턱**이다(문턱은 그 크기와 바로 아래 크기 사이). 결과는 1절의 "E7".

- **토큰 추정 보정**: `UsageLog`의 실제 `inputTokens`(제공사 usage, CHAT 행)와 같은 행에 저장된 조립기 추정(`blockTokens.total`)을 비교해 가중 배율, 중앙값, p10/p90, 직선 적합을 낸다. 코드의 환산 계수 `ESTIMATE_TO_REAL = 0.55`와 비교한다.
  - 2026-11-11 개발 DB 실행: 대상 2건(추정 520→실제 319, 705→438), 배율 0.613~0.621, 가중 0.618. 현재 계수 0.55보다 약 12% 높다. 표본이 2건이고 짧은 요청뿐이라 **계수는 바꾸지 않았다**. 계수가 실제보다 낮으면 breakpoint가 필요한 길이보다 늦게(보수적으로) 붙는다.
- **지연 비교**: 같은 10턴 시나리오를 breakpoint 끔/켬으로 돌린다. 기록은 고정된 가짜 응답으로 채워 두 방식의 프롬프트가 같다(표시만 다름). 방식·실행마다 표식을 달리해 캐시가 섞이지 않게 하고, 라운드마다 순서를 번갈아 돌린다. 출력은 방식별 ttft/total/actualCost의 p50/p95, 실제 breakpoint가 붙은 호출 수, 캐시 토큰 비중이다. 서비스 규칙(4096 환산)을 그대로 쓰면 짧은 초반 턴에는 breakpoint가 안 붙고, 그 호출 수가 표에 나온다. 결과는 아직 없다.

## 5. 하루 카드 v3 적용 메모 (2026-11-11)

## 6. 하루 카드 v3 추가분 메모 (2026-11-12)

- `haru-card-v3-addendum.md`를 `prisma/seed-data/haru.json`의 persona와 exampleDialog 끝에 덧붙였다(기존 내용 유지). 목적은 첫 턴 프롬프트를 문턱 위로 올리는 것이다.

## 7. 캐시가 깨진 원인 보기 (접두사 진단)

cached 토큰 수만으로는 적중이 안 된 이유를 알 수 없어서, 대화 호출마다 블록별 해시를 남기고 직전 턴과 비교한 결과를 `UsageLog.blockTokens.cacheBreak`에 기록한다(원문은 저장하지 않는다).

| 값 | 뜻 |
| --- | --- |
| `first` | 이 대화의 첫 대화 호출(비교 대상 없음). 이 기능 이전에 기록된 행 다음의 첫 호출도 여기에 든다 |
| `none` | 접두사 유지. 이때 cached가 0이면 원인은 프롬프트가 아니라 제공사 쪽(최소 길이 미달, TTL 만료, 라우팅)이다 |
| `fixed` | 캐릭터 카드·안전 지시가 바뀜 |
| `summary` | 요약이 생기거나 갱신됨 |
| `lorebook` | 걸린 로어북이 달라짐(`LOREBOOK_POSITION=beforeInput`이면 접두사 밖이라 기록되지 않음) |
| `recent_window` | 최근 대화 시작점이 움직임(토큰 예산 초과로 오래된 메시지가 잘린 경우 등) |
| `layout` | 로어북 위치 설정이 바뀜 |

여러 블록이 함께 바뀌면 프롬프트 순서로 가장 앞의 것 하나만 기록한다(그 뒤는 어차피 전부 무효).

원인별 적중 현황(읽기 전용):

```sql
select "blockTokens"->>'cacheBreak' as cache_break,
       count(*) as turns,
       sum(("cachedInputTokens" > 0)::int) as hit_turns,
       round(avg("cachedInputTokens"::numeric / nullif("inputTokens", 0)), 2) as avg_cached_ratio
from "UsageLog"
where kind = 'CHAT' and not "usageEstimated"
group by 1 order by 2 desc;
```

한계: 진단은 "우리가 보낸 프롬프트가 같았는가"만 본다. 실제 적중 여부는 제공사가 정하므로 `none`인데 cached=0인 턴이 곧 제공사 쪽 원인을 가리킨다. 응답이 비었거나 모델 호출이 실패한 턴은 UsageLog가 없어 비교에서 빠진다.
