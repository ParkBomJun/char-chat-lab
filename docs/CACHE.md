# 프롬프트 캐시 실측과 설계

> **이 문서의 수치는 시뮬레이션이 아닌 실측입니다. 측정일 2026-11-11(E1~E6)과 2026-11-12(E7), OpenRouter 경유 `google/gemini-3.8-flash`.**
> 측정은 사용자가 `npm run cache:probe -- --real`로 직접 실행했고, 이 문서는 그 결과를 정리한 것입니다.
> 아래에서 **"(원문 필요)"** 로 표시한 칸은 아직 원문 표(`docs/cache-probe-raw-2026-11-11.md`)가 이 저장소에 없어 비워 둔 곳입니다. 추정해서 채우지 않았습니다. 채워진 숫자는 사용자가 원문에서 옮겨 전달한 값입니다.

## 0. 결정과 근거 (2026-11-12)

두 가지를 정했다. 근거가 된 측정은 1절에 있다.

**결정 1. 캐시 표시 위치의 기본값은 `fixedBlock`(고정 블록 끝에 고정)이다.** `beforeInput`(이번 입력 직전)은 "비용 우선" 옵션으로 남긴다.

| 방식 | 10턴 누적 비용 | 첫 토큰 p50 | 캐시를 만드는 턴 |
| --- | --- | --- | --- |
| 표시 없음 | $0.0447~0.0463 (기준) | 1.6~1.9초 | 없음 |
| `beforeInput` (비용 우선) | $0.0117 (−74~75%) | 4.8~5.1초 | 매 턴 |
| `fixedBlock` (기본값) | $0.0213~0.0215 (−52~54%) | 1.4~2.1초 | 첫 턴, 그리고 고정 블록이 바뀐 턴 |
| `stepped` (옵션) | $0.0139 (−70%) | 3.1초 | 이력이 일정 토큰 늘 때마다 |

- **캐시를 만드는(쓰기가 붙는) 요청은 첫 토큰이 약 3초 느리다.** 세 번의 비교 실행에서 쓰기가 붙은 요청의 첫 토큰 p50은 4.4~5.1초, 붙지 않은 요청은 1.4~1.9초였다. `beforeInput`은 표시가 턴마다 옮겨 가서 매 턴이 캐시 생성이고, 그래서 매 턴 약 3초를 더 기다린다.
- `fixedBlock`은 첫 턴에만 캐시를 만들고 이후에는 읽기만 한다. 지연은 표시 없는 요청과 같고 비용은 절반이다. 대화 이력은 일반 요금이라 턴이 쌓일수록 `beforeInput`보다 비싸진다(10턴째 턴당 약 2.7배, 금액으로 약 $0.002 차이).
- 입력 분류기가 턴마다 약 2.3초를 쓰고 있어서, 첫 글자까지의 대기는 `beforeInput` 약 7.4초, `fixedBlock` 약 4.1초가 된다(각 p50의 합이며 직접 잰 값은 아니다). 턴당 $0.002를 아끼는 것보다 매 턴 3초가 더 크다고 보았다.
- **5분간 요청이 없으면 다음 요청이 캐시를 새로 만든다.** 같은 요청을 6분 뒤에 다시 보내자 쓰기가 앞부분 전체만큼 다시 붙었고 첫 토큰도 4.8초였다(E9). 문서상 유지 시간 5분과 맞는다. 그래서 `fixedBlock`에서도 사용자가 5분 넘게 쉬었다가 보내는 턴은 캐시 생성 요금(입력의 약 15.6%)과 약 3초의 지연을 다시 낸다. 다른 사용자가 같은 캐릭터로 그 사이에 대화했다면 그 캐시를 같이 쓴다(같은 캐릭터의 고정 블록은 대화·사용자와 무관하게 같다).

**결정 2. 로어북 전체가 작으면 고정 블록에 상시 포함한다.** 기준은 `LOREBOOK_INLINE_MAX_TOKENS`(기본 추정 1,000토큰)이고, 넘으면 예전처럼 키워드 방식이다.

- 근거: 키워드 방식에서는 로어북 항목이 걸리거나 빠지는 턴마다 캐시가 다시 만들어졌다(표시를 고정 블록에 둬도, 로어북을 입력 바로 앞으로 옮겨도 마찬가지였다). 상시 포함하면 고정 블록이 턴마다 같아서 로어북 때문에 캐시가 다시 만들어지지 않았다(1절 "로어북 상시 포함 비교").
- 조건: 활성 항목 본문의 추정 토큰 합이 기준 이하일 때만. 시드 카드 "하루"의 로어북 4개는 추정 405토큰(실제 약 233토큰)이라 상시 포함된다.
- 한계:
  - 관리자가 로어북을 수정·추가·삭제하면 고정 블록이 바뀌어 캐시가 한 번 새로 만들어진다. 항목이 늘어 기준을 넘으면 키워드 방식으로 돌아가고 그때도 한 번 새로 만들어진다.
  - 키워드와 무관한 항목까지 매 턴 들어간다. 캐시 토큰으로 싸게 청구되지만(입력의 10%), 10턴 누적 비용은 키워드 방식보다 약 1% 높았다. 이득은 비용이 아니라 캐시 재생성(약 3초 지연)이 없어지는 것이다.
  - 모델이 항상 모든 항목을 보게 되므로, 키워드가 나왔을 때만 꺼내던 설정이 관련 없는 턴에 언급될 수 있다. 응답 내용에 주는 영향은 재지 않았다.
  - 로어북이 큰 캐릭터(기준 초과)는 여전히 키워드 방식이고, 걸린 항목이 바뀌는 턴마다 캐시가 다시 만들어진다. 이 경우의 해법(로어북을 사용자 입력 쪽 참고 블록으로 보내기)은 구현하지 않았다.
  - 구조가 같아도 캐시가 다시 만들어진 관측이 1건 있다(상시 포함 방식의 재사용 기대 18회 중 1회, 원인 불명).

### 실제 서비스 대화에서의 확인 (2026-11-12)

개발 서버(`npx next dev -p 3100`, 기본값 `CACHE_MIN_TOKENS=3500`), 하루 카드 v3 + 추가분 2차, **서로 다른 새 대화의 첫 턴 두 번**(11:24 KST, 사용자가 실행). `UsageLog`(kind=CHAT, createdAt은 UTC):

| createdAt (UTC) | inputTokens | cachedInputTokens | outputTokens | actualCost | ttftMs | 구분 |
| --- | --- | --- | --- | --- | --- | --- |
| 2026-11-12 02:24:24 | 4498 | 4497 | 74 | 0.00080290 | 4310 | 캐시 생성 |
| 2026-11-12 02:24:37 | 4501 | 4497 | 86 | 0.00066277 | 1894 | 캐시 재사용 |

비교 대상(카드 확장 전, 같은 모델, 캐시 없음):

| createdAt (UTC) | inputTokens | cachedInputTokens | outputTokens | actualCost | ttftMs |
| --- | --- | --- | --- | --- | --- |
| 2026-11-11 21:01:23 | 3255 | 0 | 126 | 0.00291375 | 5886 |
| 2026-11-11 21:01:47 | 3323 | 0 | 190 | 0.00320475 | 5444 |

검산(단가 USD/1M: 입력 0.75, 출력 3.75, 캐시 읽기 0.075, 캐시 쓰기 0.041667):

```
첫 요청(생성):   1 × 0.75 + 4497 × (0.075 + 0.041667) + 74 × 3.75 = 0.00080290   ← 읽기와 쓰기가 둘 다 청구됨
둘째 요청(재사용): 4 × 0.75 + 4497 × 0.075             + 86 × 3.75 = 0.00066278   ← 읽기만 청구됨. 쓰기 요금 없음
```

- **캐시를 처음 만드는 요청은 읽기+쓰기, 유지 시간 안에 같은 앞부분이 다시 오면 읽기만 청구된다.** 이전 판정("매 요청마다 읽기+쓰기가 청구된다")은 틀렸다. cache-probe E5b/E6은 요청마다 앞부분이 달라서 재사용이 관측되지 않았던 것이다. (E5b 두 번째 요청이 왜 쓰기를 다시 냈는지는 미확인. 앞부분이 6토큰 달랐다.)
- **서로 다른 대화의 첫 턴이 같은 캐시(4,497토큰)를 나눠 썼다.** 같은 캐릭터의 첫 턴은 대화와 사용자가 달라도 재사용된다.
- **첫 토큰 지연**: 캐시 없음 5.4~5.9초, 캐시 생성 4.3초, 캐시 재사용 1.9초. 각 1~2건의 관측이고 비교 실험이 아니다.
- **비용**: 카드가 약 1,200토큰 길어졌는데 턴 비용은 72%(생성)~77%(재사용) 줄었다($0.00291375 대비).
- **토큰 환산**: 이 첫 턴의 조립기 추정은 7,615(글자 수)이고 실제는 4,498토큰이라 배율은 0.59다. 코드의 환산 계수 0.55보다 조금 높다(계수는 바꾸지 않았다).
- 한 대화에서 턴이 쌓일 때는 매 턴 쓰기가 앞부분 전체만큼 다시 붙는다(아래 "E8"). 실제 서비스 대화 4~5턴의 로그로 한 번 더 확인할 예정이다.
- 유지 시간은 E9로 확인했다(6분 뒤 만료, 아래 "E9").

### E8: 한 대화가 이어질 때 (2026-11-12 11:43 KST)

`npm run cache:probe -- --real --only E8`. 하루 고정 블록 앞에 실행별 표식을 붙여 새 앞부분으로 시작하고, 요청 4개를 순서대로 보냈다. 각 요청은 이전 요청 전체에 새 턴(가짜 응답 1개와 새 사용자 입력 1개)을 붙인 것이고, 표시는 서비스처럼 새 입력 바로 앞 메시지에 붙였다(턴마다 표시 위치가 뒤로 옮겨 간다). 로어북은 넣지 않았다. max_tokens=64, 호출 4회, 실제 청구액 합계 $0.00308.

| 요청 | prompt | 늘어난 입력 | cached | cacheWr | cost($) | ttft(ms) | ms |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1턴째 | 4550 | - | 4545 | 4545 | 0.000759 | 4677 | 5145 |
| 2턴째 | 4614 | 64 | 4608 | 4608 | 0.0007671 | 5159 | 5801 |
| 3턴째 | 4670 | 56 | 4664 | 4664 | 0.00077363 | 4763 | 5453 |
| 4턴째 | 4722 | 52 | 4715 | 4715 | 0.00078033 | 4360 | 4828 |

- **턴마다 쓰기가 앞부분 전체만큼 다시 붙는다.** 2~4턴째도 `cacheWr = cached = 표시까지의 앞부분 전체`였다. 늘어난 50~60토큰만 새로 쓰는 것이 아니고, 이전 턴의 캐시를 읽기만 하지도 않는다.
- 검산(2턴째 입력 청구액 0.0005421): 비캐시 6 × 0.75 + 4,608 × (0.075 + 0.041667) = 542.1 [÷ 1,000,000]. 네 요청 모두 "앞부분 전체에 읽기+쓰기"로 맞는다.
- 즉 **이어지는 대화의 매 턴은 "캐시 생성" 요청이다.** 표시 위치가 턴마다 달라져서 매번 새 캐시를 만드는 것으로 보인다. 읽기만 내는 재사용은 표시까지의 앞부분이 완전히 같은 요청이 다시 올 때만 일어난다(같은 캐릭터의 첫 턴, 같은 요청의 재시도).
- 그래도 턴 비용은 일반 요금보다 싸다: 앞부분 전체가 입력 단가의 약 15.6%로 청구된다(4턴째 입력 $0.00055533, 표시가 없었다면 4,722 × 0.75 = $0.0035415).
- **첫 토큰 지연은 줄지 않았다**: 4.4~5.2초로, 실제 대화에서 본 "캐시 생성 4.3초"와 같은 수준이다. 재사용에서 본 1.9초는 이어지는 대화에서는 나오지 않는다(각 1회 관측).
- 이 표만으로는 2턴째가 1턴째의 캐시를 일부라도 읽었는지 알 수 없다(cached와 cacheWr가 같은 값이라 구분되지 않는다). 청구는 어느 쪽이든 읽기+쓰기다.

**설계에 주는 의미(계산)**: 표시를 고정 블록 끝에 고정해 두면 고정 블록은 매 턴 읽기만(10%) 내지만 그 뒤의 대화 이력은 일반 요금(100%)이 된다. 지금처럼 표시를 새 입력 직전으로 옮기면 전체 앞부분이 15.6%다. 고정 블록을 F, 표시까지의 앞부분을 P라 하면 `0.1167 × P = 0.075 × F + 0.75 × (P − F)`에서 P ≈ 1.066 × F가 갈림점이다. 이력이 고정 블록의 약 7%(하루 카드 기준 약 300토큰)를 넘으면 지금 방식이 더 싸다. 두 방식을 실제로 나란히 잰 결과는 다음 절이다.

### 비용 검산

단가(2026-11-11 OpenRouter 확인, USD/1M): 입력 0.75, 출력 3.75, 캐시 읽기 0.075, 캐시 쓰기 0.041667.

```
비캐시 토큰 × 0.75 + 캐시 읽기 토큰 × 0.075 + 캐시 쓰기 토큰 × 0.041667 + 출력 토큰 × 3.75   (÷ 1,000,000)
  = 실제 청구액(usage.cost)   ← 캐시 생성 요청과 재사용 요청 모두 일치(위 절, 테스트로 고정)
```

- 캐시를 만드는 요청에서는 `cached`와 `cache_write`가 **같은 토큰**이고 그 토큰에 읽기 단가와 쓰기 단가가 둘 다 붙는다. 이때 캐시 토큰 단가는 입력 단가의 약 15.6%다(0.116667 / 0.75).
- 재사용하는 요청에서는 `cache_write`가 0이고 읽기 단가만 붙는다. 캐시 토큰 단가는 입력 단가의 10%다.
- 그래서 비캐시 토큰 수는 `입력 − max(캐시 읽기, 캐시 쓰기)`로 계산한다.

## 2. 판정

- **확인된 것**
  - 암시적(자동) 캐시는 믿고 설계할 수 없다. 같은 요청을 연달아 보낸 실험(11.5K)에서는 0이었고, 이어지는 10턴 대화에서는 표시 없이 20회 중 5회만 잡혔다(잡힌 턴은 읽기 단가로 청구).
  - 명시적 `cache_control`은 3,555토큰 이하(1,754 / 3,555)에서 실패, 4,159토큰 이상(4,159 / 5,799)에서 동작했다. 문턱은 3,555~4,159 사이다.
  - **캐시 생성과 재사용은 청구가 다르다(2026-11-12 정정).** 캐시를 처음 만드는 요청은 `cached = cacheWr`이고 읽기+쓰기 단가(입력의 약 15.6%)가, 유지 시간 안에 같은 앞부분이 다시 온 요청은 `cacheWr = 0`이고 읽기 단가(10%)만 청구된다. 2026-11-11의 E6 판정("매 요청 할인": `cache_control`을 붙인 요청은 매번 읽기+쓰기로 청구된다)은 틀렸다. E6은 앞부분이 서로 다른 요청 두 개를 각각 처음 보낸 것이라 둘 다 "생성"이었을 뿐이다.
  - 같은 캐릭터의 첫 턴은 대화와 사용자가 달라도 같은 캐시를 재사용한다.
  - **이어지는 대화의 매 턴은 생성 요청이다(E8).** 표시가 새 입력 직전으로 옮겨 가므로 턴마다 앞부분 전체에 읽기+쓰기가 붙는다. 재사용(읽기만)은 표시까지의 앞부분이 완전히 같을 때만 일어난다.
- **의미**
  - `cachedInputTokens`는 생성 요청에도 잡히므로 "캐시 토큰 비중"만으로는 재사용을 알 수 없다. 재사용 여부는 **쓰기 토큰이 0인지**로 가른다. 그래서 `UsageLog.cacheWriteTokens`를 따로 저장하고 `/admin`은 대화 호출을 "생성(쓰기 발생)"과 "재사용(읽기만)"으로 나눠 보여 준다.
  - 효과는 **비용**(`actualCost`)과 **지연**(ttft)으로 판단한다. 나란히 잰 결과(1절 "세 방식 비교"): 캐시를 만드는 요청은 첫 토큰이 약 3.3초 늦고, 읽기만 하는 요청은 표시 없는 요청과 같다.
  - 앞부분이 달라지면(로어북이 바뀌는 턴, 요약이 갱신되는 턴) 캐시를 새로 만들어야 하므로 읽기+쓰기를 다시 낸다. 로어북 위치(`afterFixed`)가 재사용에 주는 영향은 다시 봐야 하는 문제로 돌아왔다(미측정). 대화가 이어지는 턴은 어차피 매번 생성이므로(E8), 로어북이 바뀌어도 청구 방식은 같을 것으로 예상한다(예상이며 미측정).

- **전송 안전**: 어댑터는 주소가 `openrouter.ai`일 때만 `cache_control`을 보낸다(`supportsExplicitCache`). 다른 OpenAI 호환 서버에서는 표시를 떼고 일반 문자열 content로 보낸다. 내부 표시 필드는 어느 경우에도 제공사로 새지 않는다. 끄려면 `CACHE_BREAKPOINT=0`.
- **추정 비용(`estCost`)**: `(입력 − max(캐시읽기, 캐시쓰기))×입력 + 캐시읽기×읽기 + 캐시쓰기×쓰기 + 출력×출력`, `cacheWritePer1M`이 없으면 쓰기 항목은 0. 생성 요청(쓰기 토큰 = 읽기 토큰)과 재사용 요청(쓰기 토큰 0) 모두 실제 청구액과 일치하는 것을 테스트로 고정했다(`src/lib/pricing.test.ts`). 캐시 쓰기 토큰이 읽기 토큰과 **겹친다는 가정**이며 이 모델·경로에서만 검산했다. 실제 청구액(`actualCost`)이 있으면 `/admin`은 그것을 쓰고 `estCost`는 비교용이다.
- **기록**: `UsageLog.cacheWriteTokens`(2026-11-12 추가). 제공사 usage의 `cache_write_tokens`를 저장한다. 0보다 크면 캐시 생성, `cachedInputTokens > 0`인데 0이면 재사용이다. 컬럼을 추가하기 전의 행은 NULL이라 `/admin`에서 "구분 불가"로 센다.
- **한계**: 세션 요약이 바뀌는 시점(`SUMMARY_EVERY`마다)에는 접두사가 달라진다. 유지 시간은 문서상 5분이고 갱신되지 않는다. 6분 뒤 만료는 E9로 확인했다. `session_id`는 아직 요청에 넣지 않는다. 캐시를 만드는 요청은 그 앞부분이 읽기+쓰기 단가(입력의 약 15.6%)로, 재사용하는 요청은 읽기 단가(10%)로 청구되고, 문턱에 못 미치면 표시가 붙어도 일반 단가(100%)다(E7).

- **E7(문턱)**: `cache_control`을 붙인 요청을 약 2.5K, 3.2K, 3.6K, 4.2K토큰으로 1회씩 보낸다. 크기는 영문 더미 텍스트의 글자 수로 맞춘 근사치라서(더미 약 3.16글자/토큰, 2026-11-11 E4·E5 실측에서 역산) 표의 `prompt` 열(제공사가 센 값)을 기준으로 읽는다. 요청마다 맨 앞에 실행별 표식을 넣어 이전 요청의 캐시와 겹치지 않는다. 문턱을 넘으면 캐시를 만드는 첫 요청부터 cached = cacheWr > 0이 보이므로 **처음 cached>0이 되는 크기가 문턱**이다(문턱은 그 크기와 바로 아래 크기 사이). 결과는 1절의 "E7".
- **E8(이어지는 대화)**: 하루 고정 블록(실제 약 4.4K토큰) 앞에 실행별 표식을 붙여 새 앞부분으로 시작하고, 요청 4개를 순서대로 보낸다. 각 요청은 이전 요청 전체에 새 턴(가짜 응답 1개와 새 사용자 입력 1개)을 붙인 것이고, 표시는 서비스처럼 새 입력 바로 앞 메시지에 붙인다. 로어북은 넣지 않는다. 표에 prompt, 늘어난 입력, cached, cacheWr, cost, ttft가 나온다. 볼 것: 2턴째부터 cacheWr가 **앞부분 전체만큼 다시 붙는지, 늘어난 부분만 붙는지, 붙지 않는지**. 결과는 1절의 "E8"(앞부분 전체만큼 다시 붙는다).
- **E9(유지 시간)**: 같은 요청을 6분 간격으로 2회 보낸다(문서상 TTL 5분 확인용). 둘째 요청이 cached > 0, cacheWr = 0이면 그 간격에도 유지된 것이고, cacheWr > 0이면 만료돼 다시 만든 것이다. 결과는 1절의 "E9"(6분 뒤 만료).

- **토큰 추정 보정**: `UsageLog`의 실제 `inputTokens`(제공사 usage, CHAT 행)와 같은 행에 저장된 조립기 추정(`blockTokens.total`)을 비교해 가중 배율, 중앙값, p10/p90, 직선 적합을 낸다. 코드의 환산 계수 `ESTIMATE_TO_REAL = 0.55`와 비교한다.
  - 2026-11-11 개발 DB 실행: 대상 2건(추정 520→실제 319, 705→438), 배율 0.613~0.621, 가중 0.618. 현재 계수 0.55보다 약 12% 높다. 표본이 2건이고 짧은 요청뿐이라 **계수는 바꾸지 않았다**. 계수가 실제보다 낮으면 breakpoint가 필요한 길이보다 늦게(보수적으로) 붙는다.
- **표시 위치는 `fixedBlock`으로 정했다(0절).** 비교한 선택지: ① `beforeInput` — 비용 최저(10턴 누적 −74%), 매 턴 첫 토큰 약 +3초. ② `fixedBlock` — 비용 −52%, 지연은 표시 없음과 같음(생성 턴 제외). ③ `stepped` — 비용 −70%, 쓰기가 붙는 턴만 약 +3초.
- **지연 비교**: 같은 10턴 시나리오를 네 방식(표시 없음 / beforeInput / fixedBlock / stepped)으로 돌린다. 실행 전에 예상 호출 수와 비용을 출력한다. 기록은 고정된 가짜 응답으로 채워 두 방식의 프롬프트가 같다(표시만 다름). 방식·실행마다 표식을 달리해 캐시가 섞이지 않게 하고, 라운드마다 순서를 번갈아 돌린다. 출력은 방식별 ttft/total/actualCost의 p50/p95, 실제 breakpoint가 붙은 호출 수, 캐시 토큰 비중이다. 서비스 규칙(3500 환산)을 그대로 쓰면 짧은 초반 턴에는 breakpoint가 안 붙고, 그 호출 수가 표에 나온다. 결과는 1절 "세 방식 비교".

## 7. 캐시가 깨진 원인 보기 (접두사 진단)

cached 토큰 수만으로는 적중이 안 된 이유를 알 수 없어서, 대화 호출마다 블록별 해시를 남기고 직전 턴과 비교한 결과를 `UsageLog.blockTokens.cacheBreak`에 기록한다(원문은 저장하지 않는다).

| 값 | 뜻 |
| --- | --- |
| `first` | 이 대화의 첫 대화 호출(비교 대상 없음). 이 기능 이전에 기록된 행 다음의 첫 호출도 여기에 든다 |
| `none` | 접두사 유지. 이때 cached가 0이면 원인은 프롬프트가 아니라 제공사 쪽(최소 길이 미달, TTL 만료, 라우팅)이다 |
| `fixed` | 캐릭터 카드·안전 지시가 바뀜 |
| `summary` | 요약이 생기거나 갱신됨 |
| `lorebook` | 걸린 로어북이 달라짐(`LOREBOOK_POSITION=beforeInput`이면 접두사 밖이라 기록되지 않음) |
| `recent_window` | 최근 대화 시작점이 움직임(토큰 예산 초과로 오래된 메시지가 잘린 경우 등) |
| `layout` | 로어북 위치 설정이 바뀜 |

여러 블록이 함께 바뀌면 프롬프트 순서로 가장 앞의 것 하나만 기록한다(그 뒤는 어차피 전부 무효).

원인별 적중 현황(읽기 전용):

```sql
select "blockTokens"->>'cacheBreak' as cache_break,
       count(*) as turns,
       sum(("cachedInputTokens" > 0)::int) as hit_turns,
       round(avg("cachedInputTokens"::numeric / nullif("inputTokens", 0)), 2) as avg_cached_ratio
from "UsageLog"
where kind = 'CHAT' and not "usageEstimated"
group by 1 order by 2 desc;
```

한계: 진단은 "우리가 보낸 프롬프트가 같았는가"만 본다. 실제 적중 여부는 제공사가 정하므로 `none`인데 cached=0인 턴이 곧 제공사 쪽 원인을 가리킨다. 응답이 비었거나 모델 호출이 실패한 턴은 UsageLog가 없어 비교에서 빠진다.
